Runtime Architecture

The service graph is intentionally distributed. Preserve the existing creators and teardown paths unless a lifecycle refactor is explicitly planned.

02 / SYSTEM MAP

The important boundary is lifecycle, not just access. Game::set* registers pointers; it does not define who deletes them.

Ownership invariant: do not introduce isolated smart-pointer ownership into the existing raw-pointer service graph as a side effect of gameplay work. A lifecycle migration needs its own scope, creator/destructor plan, and tests.

Creation path

Main creates major managers, initializes globals, loads databases and maps, then starts normal or headless execution.

Disposal path

Simulation owns its action center and object manager. Other services follow their existing creator and teardown path.

Decision record: 0001-runtime-ownership-model.md.

Simulation Contract

Reason about gameplay in fixed ticks. A render update can execute zero, one, or several simulation ticks.

Influence, Visibility, And Placement

Spatial systems are shared simulation state. A feature that adds movement, spawning, disposal, targeting, or placement must account for refresh and invalidation order.

05 / SPATIAL STATE

Snapshot maps

Building presence, unit presence, army presence, and unboosted-resource activity are rebuilt from current entities at scheduled cadences.

History maps

Gathering, economy, and attack activity buffer events, then merge using decay. Fresh events may wait for the scheduled history update.

Visibility map

NONE means never seen, SEEN means explored but not visible, and VISIBLE means currently visible.

Save And Load Contract

A scene save is a SQLite snapshot of gameplay plus enough continuation state to resume simulation. It is not only a picture of the map.

Physical uid identifies a runtime entity; id_db identifies a gameplay definition. Do not mix them.

Save schema rule: update SQLConsts.h, the matching column enum, saver bindings, loader DTO bindings, count assertions, tests, and migration policy together. Save loading is insensitive to physical SQLite column order, but enum names and binding order are not optional.
current limitation

No active schema version

Compatibility is inferred from required tables and columns. Adding a required field needs explicit migration or save regeneration.

current limitation

Existing save replacement

The saver does not replace an existing database; creating tables without IF NOT EXISTS makes overwrite fail.

08 / CHOICES
P1

Make ordinary building decisions functional

Replace the non-resource buildings.at(0) fallback with deliberate defence, tech, home, and unit-production selection.

high valuemedium scope
Why it matters

Master outputs for defence, tech, and other buildings are currently disabled. Re-enabling them without real selection can produce the wrong structure.

Candidate shape

Model building capabilities and prerequisites in data, then rank candidates deterministically or through a dedicated output. Reuse the resource capability pattern where possible.

Dependencies

Building definitions, prerequisites, readiness rules, AI request paths, placement behavior, and possibly new CSV outputs.

First experiment

Add a pure selection function for one category, such as defence, with a table-driven test. Do not re-enable every Master path at once.

Start at AiOrchestrator.cpp and WantExecutor.cpp.

P2

Close producer dependency gaps

Handle producers that exist but are not ready, under-levelled, or competing with other upgrades.

high valuelow-medium scope
Current behavior

The fallback checks whether any producer type exists, then queues the original request. Producer readiness is checked later, and the original request may be lost for that pass.

Candidate shape

Represent producer status explicitly: absent, building, not ready, ready, insufficient level, or blocked by cost. Route the next useful upgrade or retry without creating loops.

Risks

Want priority, soft reserves, queue capacity, and save/load of wants can all change. A fallback graph deeper than one hop can loop.

First experiment

Write deterministic tests for one unit with an absent producer, a building producer, and an under-levelled producer. Keep the fallback one-hop until behavior is measured.

Known TODO: AiOrchestrator.cpp near tryUnitWant(); flow diagram: want_fallback_flow.html.

P3

Add retreat and real combat outcomes

Make the army capable of preserving strength and make AI history describe what happened, not only what was ordered.

behavior riskmedium scope
Current gap

There is no health-threshold withdrawal or regroup behavior. Attack history records an order as success, not whether an engagement was won.

Decisions first

Define retreat threshold, safe destination, regroup condition, command-priority interaction, and whether outcome history needs new enum values.

Useful signals

Own health, nearby enemy pressure, recent losses, distance to own economy/buildings, battle activity, and target visibility.

First experiment

Instrument a headless match with order-issued, combat-started, unit-lost, and target-destroyed events before changing decisions.

Start at AiOrchestrator::order(), AiHistoryEnums.h, and army_targeting_flow.html.

P4

Make scouting and fog of war meaningful

Add last-seen knowledge and stop strategic decisions from using information the player could not have obtained.

large designdecision heavy
This is more than scout orders

Meaningful scouting needs scout behavior, last-seen positions and timestamps, known versus global enemy state, visibility-aware centers, and persistence decisions.

State design

Decide whether memory belongs per player, per map cell, or per entity class. Decide how stale knowledge decays and what a loaded save remembers.

AI contract impact

Enemy inputs currently use the selected enemy's current possession. Visibility-limited inputs may change normalization and every affected brain CSV.

First experiment

Prototype a last-seen record outside the neural network and render it in debug mode. Validate semantics before changing brain inputs.

Relevant code: VisibilityManager.cpp and MasterBrain.cpp.

P5

Improve worker adaptation and expansion

Make the economy respond faster to shortages, travel costs, node depletion, and strategic expansion needs.

visible payoffmedium scope
Current gap

Only one busy worker is reassigned per order phase under a low-priority condition. Expansion urgency influences placement indirectly but does not initiate an expansion request.

Candidate improvements

Use travel time, resource depletion, node safety, and available capacity. Consider resource-specific spatial outputs instead of one aggregate unboosted-resource signal.

Data questions

Are queue durations and reload values tick counts or seconds? Can resource metrics remain in their normalized ranges after new signals are added?

First experiment

Log worker reassignment reason, distance, resource priority, and result. Compare one-worker and bounded multi-worker policies in the same headless scenario.

References: AiOrchestrator.cpp, resource_gathering_schema.html, and influence_maps_deep_dive.html.

P6

Formalize save versioning and migration

Turn the current required-column contract into an explicit versioned policy before adding more long-lived state.

reliabilitymedium scope
Why now

Scouting memory, richer AI outcomes, and multiplayer state will all need persistence. Without a schema version, every required field creates a manual compatibility decision.

Policy choices

Choose supported versions, migration direction, whether saves are upgraded in place or copied, and whether incompatible saves are rejected early.

Reliability choices

Decide whether saving replaces files atomically, whether it is restricted to safe simulation boundaries, and how broken UID references are diagnosed.

First experiment

Add a version value to a copy of the config contract and write a migration test for one documented legacy format. Do not alter live saves until policy is agreed.

References: SQLConsts.h, SceneLoader.cpp, old-save-migration.txt, and config-table-migration.txt.

P7

Generalize beyond two players

Replace the hard-coded single-enemy model with threat selection and multi-opponent state.

large scopearchitecture risk
Current assumption

Enemy selection and influence ownership derive from a two-player world. This is a data and AI-interface change, not only a new loop.

Systems affected

PlayersManager, enemy inputs, influence-map slots, military centers, visibility, scores, target selection, and save state.

Decision first

Choose whether brains see one selected threat, aggregated threats, a fixed number of opponents, or a separate opponent-selection layer.

First experiment

Make threat selection a pure function over three mocked players. Keep the existing two-player runtime behind the function until the policy is clear.

Start at PlayersManager.cpp and InfluenceManager.cpp.

P8

Harden or replace the AI runtime

Choose between strengthening the existing CSV runtime and migrating to a validated model format such as ONNX.

long horizondecision heavy
Lower-risk path

Validate every layer's dimensions, bias shape, and topology; add model metadata; improve diagnostics; preserve the current trainer and CSV compatibility.

Large path

A hierarchical policy network with shared features and multiple heads could reduce manual routing. ONNX Runtime or LibTorch could replace fragile parsing and inference.

Hidden work

Windows packaging, deterministic inference, model versioning, training export, trainer updates, weight reproducibility, and candidate compatibility gates.

First experiment

Build a topology validator that reports layer widths and bias shapes for all five current CSV brains. Use it before considering a runtime replacement.

References: ideas.txt, ai-development.md, Layer.cpp, and gen_brain_csv.ps1.
