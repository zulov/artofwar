Technology and Upgrade Design

A design for making progression broader than “level this unit” or “level this building”: player-wide technologies, branching doctrines, counter-tech, trade-offs, and long-term strategic identity.

1. Short Version

Recommendation: keep unit/building levels and introduce a separate player-owned technology system. Levels improve one concrete database entity. Technologies affect a class of entities, a relationship between classes, the economy, production, or the available rules of the game.

For the example “bonus for all melee attack,” add a technology such as Tempered Blades. It should not point to a specific unit ID. It should match units through the existing unit tags, such as typeMelee, and apply its modifier when damage is calculated.

Tempered Blades
  owner: Player 1
  filter: own unit has typeMelee
  effect: attack multiplier +10%
  timing: applies to existing and newly created units
  prerequisite: Blacksmith level 1
  cost: food + wood + gold
  research: player queue

This creates a strategic choice. A player is no longer only deciding which unit to level. The player is deciding what kind of army, economy, defense, or timing attack the whole civilization is building toward.

2. Current System And Its Boundary

The current implementation has a useful foundation, but it is primarily an entity-definition level system:

Current conceptMeaningRuntime shapeGood for
Unit levelA player-wide level for one unit database definition.Player::unitLevels[id] selects a db_unit_level.Improve swordsman level 1 to swordsman level 2.
Building levelA player-wide level for one building database definition.Player::buildingLevels[id] selects a db_building_level.Improve one barracks or one resource-building type.
Building queueA queue owned by a building for production and unit upgrades.QueueManager and QueueElement.Train units or level a unit through a ready producer.
Player queueA queue owned by the player for building upgrades.Player::queue.Research-like work already has a natural owner.
Unit combat tagsBoolean categories such as melee, infantry, cavalry, heavy, and light.Fields on db_unit.Targeting and bonuses against categories.

Unit level data already contains category bonuses. However, the existing bonus_melee value is used by Unit::getAttackVal() as a bonus against a melee target. It is not a player-wide bonus for melee attackers. A new technology system should make the two directions explicit:

Attacker filter

own unit has typeMelee

“All melee units deal +10% damage.”

Target filter

enemy unit has typeMelee

“All units deal +10% damage against melee.”

The current flow is excellent for direct type progression. The proposed technology layer adds a second branch rather than replacing this one.

3. Design Principles

1. Separate identity from scope

A unit level targets one unit definition. A technology targets a filter, relationship, rule, or capability. Do not encode global bonuses by copying values into every unit level.

2. Prefer meaningful choices

A technology should create a decision: faster pressure, stronger defense, better economy, a counter, a new unit, or a trade-off. Avoid a tree where every node is an automatic universal bonus.

3. Make filters visible

The player should understand exactly who benefits. “Melee attackers” and “damage against melee targets” are different effects and should be displayed differently.

4. Keep calculations deterministic

Effects should be resolved from completed player technologies and static database definitions. Avoid hidden per-unit mutation when a calculation-time modifier is sufficient.

5. Use existing categories first

Existing unit tags such as melee, infantry, cavalry, heavy, light, range, worker, and special already provide useful grouping without requiring a new class system.

6. Build a small core first

Start with a handful of effect types and one exclusive branch. A generic effect system can grow later after the queue, save, UI, and balance rules are proven.

4. Three Progression Layers

The game can have three related but distinct progression layers. Each solves a different design problem.

LayerQuestion it answersExampleScopeRecommended behavior
Entity levelHow does this unit/building definition become better?Spearman level 2 gains HP and attack.One unit or building ID.Keep the current level tables and level queues.
TechnologyWhat capability or specialization has the player researched?All melee units gain +10% attack.Player-wide filter or rule.Add a dedicated research queue and unlock state.
DoctrineWhat strategic identity has the player committed to?Shock doctrine improves speed and attack but reduces armor.Player-wide mutually exclusive branch.Use exclusive groups and irreversible choices, at least initially.
Do not make every technology permanent power stacking. If every branch can be completed, the late game converges to the same fully upgraded civilization. Use limited research slots, exclusive doctrines, escalating costs, or situational technologies to preserve differentiation.

The layers combine at gameplay calculation points, but they should remain separately owned and persisted.

5. Technology Model

5.1 A technology is a player-owned rule package

A technology should define its identity, cost, prerequisites, research location, effects, and optional exclusive group. The player stores completion state. A unit does not store a copied list of every technology that affected it.

Technology
  id: 12
  name: "Tempered Blades"
  tier: 1
  research_building: BLACKSMITH
  cost: 100 wood, 75 gold
  research_time: 180 ticks
  prerequisites: []
  exclusive_group: "offense_doctrine"  // optional
  effects:
    - own_unit_tag = MELEE
      stat = ATTACK_PERCENT
      value = 0.10

5.3 Recommended first effect vocabulary

Use a constrained enum-based system first. It is easier to validate, balance, expose to the UI, and consume from AI than a free-form expression language.

GATHER_PERCENTWorkers gather +10% faster.Resource collection calculation
COST_PERCENTInfantry cost 10% less food.Cost resolution before queue insertion

Clarify stacking. A good default is to add all additive bonuses first, then apply multipliers, then clamp values. For example: base attack 10, +10% from level bonus and +10% from technology gives 12, not 12.1 or 10.21. Write the rule down before adding many effect types.

final value = clamp((base value + additive bonuses) × (1 + percentage bonuses), minimum, maximum)

6. Research Flow

Add a dedicated TECH_RESEARCH queue action. Do not reuse the unfinished UNIT_UPGRADE value: a technology is not an upgrade of one unit definition, and its completion changes player-wide rules.

The first implementation can use the existing player queue. A later version can give each University or Blacksmith its own research queue.

6.1 Player queue or building queue?

OptionAdvantagesCosts and risksRecommendation

7. Effect Matching And Combat Examples

7.1 Effect matching

At a calculation point, the game should ask a small, explicit question: which completed player effects match this source, target, and context?

This calculation-time approach means existing and newly created units receive the same completed player technology without rewriting every unit instance.

7.2 Attack formula

Keep the existing level and target bonuses, then add technology bonuses at the same calculation boundary:

base = unit database level attack
levelTargetBonus = existing bonus against target type
technologyBonus = player effects matching source, target, and context

finalAttack = base * (1 + levelTargetBonus + technologyBonus)

For a more sophisticated future system, use separate buckets:

finalAttack = base
            * (1 + additiveAttackBonuses)
            * (1 + targetSpecificBonuses)
            * stanceMultiplier

Choose one formula and use it consistently. The examples in this document are design values, not final balance values.

9. Different Upgrade Styles

Use a mix of these styles. A healthy technology roster should contain direct power, counters, economic choices, unlocks, and rules that change how the player approaches the map.

StyleExampleStrategic questionBalance risk
Global category bonusAll melee units +10% attack.Am I committing to melee?Can become an automatic best choice if too broad.
Source-target counterRanged units +15% damage against cavalry.What is the enemy likely to build?Weak if scouting is absent or enemy composition is unknown.
Stat trade-off+12% attack, -5% armor.Do I want speed and pressure or staying power?Harder to explain and tune.
Production transformationUnits train 15% faster but cost 5% more food.Can my economy sustain tempo?May snowball if both bonuses are too strong.
Unlock technologyUnlocks a fast but fragile cavalry unit.Do I spend now to access a new plan?Must validate all ownership and producer paths.
Infrastructure bonusDefensive buildings gain HP or range.Can I hold a location?Static defense can make games stall.
Map interactionWorkers gather +20% near owned storage buildings.Where should I place infrastructure?Placement and pathing can dominate balance.
Formation or army ruleInfantry in formation take less damage from the front.Can I use the formation system well?Requires clear feedback and formation testing.
Conditional timingUnits below 50% HP gain +10% speed.Do I retreat or commit?Can produce unintuitive combat outcomes.
Temporary doctrineActivate “Forced March” for 30 seconds; units move faster but fatigue.When is the timing window?Needs cooldown and save semantics.
Choice rewardChoose attack range, damage, or cheaper production for one unit tag.What does this army need now?More UI and state complexity.
Information technologyReveal enemy army category but not exact position.Can I make a better strategic decision?Current enemy information is already unusually complete for AI.

Example: economic trade-off

Pack Animals: workers gather 10% faster.

Cost: unit production uses 5% more food.

Use when expanding the economy or preparing a long game. Avoid when early military timing is critical.

Example: counter investment

Hunter Doctrine: ranged units deal 15% more damage to cavalry.

No bonus against infantry or buildings.

Strong when scouting identifies cavalry, but a bad automatic choice against another army.

Example: positional technology

Field Fortifications: units within influence of a defensive building gain 8% armor.

No effect while fighting away from the network.

Makes map control and building placement matter instead of only increasing army stats.

Example: behavior change

Salvage Engineering: destroying an enemy building refunds a percentage of its resource value.

Units deal 5% less damage to buildings.

Encourages repeated raids and creates a different siege economy.

10. Proposed Database Schema

Runtime definitions belong in game/Data/Database/data.db. Keep technology definitions separate from unit and building level rows. The data loader currently uses SELECT * with ordinal enums, so any data-table column change must update the matching enum and constructor binding together.

Definition tables belong to data.db; completed player state belongs to the scene save. Do not duplicate effects into every unit row.

10.1 Suggested columns

TableRequired first versionLater extension
technologyid, name, icon, tier, cost fields, research time, required building category, exclusive group.nation restrictions, repeatable flag, display order, AI weight.
technology_prerequisitetechnology ID and required technology ID.OR groups, minimum building levels, resource thresholds.
technology_effecttechnology ID, effect enum, source tag, target tag, value.building/resource tags, context, condition, secondary value, cap.
technology_variantNot needed if the first tree has fixed effects.Choice-based rewards such as attack, range, or cost.

Database invariant: technology IDs become runtime keys once they appear in player save state. Keep IDs stable and dense enough for the chosen lookup structure. References must point to existing technology rows.

11. Save And Load

Completed technologies are persistent player state, not static database data. Add a dedicated optional save table rather than overloading player_levels, which currently represents unit and building levels using a type and definition ID.

CREATE TABLE player_technologies (
    player INT NOT NULL,
    technology INT NOT NULL,
    state INT NOT NULL,
    completed_tick INT NOT NULL,
    PRIMARY KEY (player, technology)
) WITHOUT ROWID;

The effect registry can be rebuilt after loading completed technology IDs; there is no need to persist a copied modifier list.

Save checklist

  • Update SQLConsts.h, db_columns.h, save table mapping, row DTOs, saver bindings, and loader bindings together.
  • Persist completed technologies and in-progress research queues if a save can happen during research.
  • Restore technology state after players exist and before gameplay calculations resume.
  • Validate that every saved technology ID exists in the loaded data.db.
  • Decide whether temporary technologies store remaining duration, activation time, or are excluded from the first release.
  • Test a save with completed technology, active research, prerequisite branches, and an exclusive doctrine.

12. UI And AI

12.1 UI proposal

Add a Research panel rather than mixing technologies into the current unit-level icon list. The panel should make the strategic consequences readable before the player pays.

UI elementInformation to show
Technology cardIcon, name, tier, short effect summary, cost, time, required building.
Effect detailSource filter and target filter separately: “melee attackers” versus “against melee targets.”
Prerequisite stateCompleted, missing prerequisite, missing building, insufficient resource, blocked exclusive group.
Research queueCurrent technology, progress, remaining time, cancel policy, and whether the cost is refundable.
Active effectsA compact list of completed technologies with the units/buildings they affect.
Choice dialogFor variants, compare choices side by side and explain that the choice is permanent or reversible.

12.2 AI proposal without immediately changing neural-network dimensions

The current AI already exposes TECH_URGENCY, but adding one brain output for every technology would require changing CSV dimensions, regenerating weights, and updating the external trainer. Start with a deterministic technology selector driven by existing urgency and game state.

technology_score =
      base_tech_urgency
    + army_match_bonus
    + enemy_counter_bonus
    + economy_match_bonus
    + prerequisite_progress_bonus
    - resource_opportunity_cost
    - duplicate_effect_penalty
AI situationPreferred researchReason
Mostly melee armyTempered Blades or Long Haft WeaponsImprove the composition the AI already chose.
Enemy cavalry pressureHunter Doctrine or Counter Drills vs cavalryRespond to observed enemy composition.
Strong economy, weak armyMilitary technologyConvert economic lead into battlefield strength.
Under attack at homeReinforced Mail or Fortress NetworkPrioritize survival and defensive positions.
Long quiet gamePack Animals or Applied MathematicsInvest in compounding economic advantage.

Later, add three preference outputs rather than one output per technology: MILITARY_TECH_PREFERENCE, ECONOMY_TECH_PREFERENCE, and DEFENSIVE_TECH_PREFERENCE. That preserves a compact brain interface.

AI data contract: if a brain enum or output width changes, update C++ enums, all compatible CSV files, focused dimension tests, and the external trainer together. A technology feature does not need a neural-network interface change in its first version.

13. Implementation Phases

Build the smallest complete vertical slice first. Do not begin with every possible effect or a fully generic scripting language.

1

Player technology state

Add a technology collection to Player, with queries such as hasTechnology(id) and getTechnologyEffects(). Keep ownership/lifecycle consistent with the existing raw-pointer service graph.

Verification: deterministic tests for unlock, duplicate completion, unknown ID, and exclusive group rejection.

2

Three fixed effects

Implement only ATTACK_PERCENT, GATHER_PERCENT, and ARMOR_PERCENT. Use existing unit tags and apply effects at combat/resource calculation points.

Verification: melee-only attack bonus, non-melee unaffected, existing units and future units both affected, armor and gather values remain in valid ranges.

3

Technology research queue

Add TECH_RESEARCH, research cost validation, fixed-tick progress, completion command, prerequisite validation, and one required building category.

Verification: no duplicate queue entries, no completion before required ticks, deferred command ordering, insufficient resources, and missing research building.

4

Data-driven definitions

Add the technology, prerequisite, and effect tables to data.db. Update ordinal column enums and constructors together. Start with 8-12 technologies.

Verification: database referential integrity, stable IDs, level/building relationship checks, and runtime load from the game working directory.

5

Save/load

Add player_technologies and preserve in-progress research. Rebuild active effects after loading player state.

Verification: save/load with completed technology, active queue, exclusive branch, and existing unit/building levels.

6

Research UI

Add technology cards, prerequisites, costs, queue progress, active effects, and locked reasons. Reuse the established Urho3D UI patterns.

Verification: long names, missing icons, mobile/window resizing, disabled actions, and correct effect descriptions.

7

AI selection

Use deterministic scoring with existing TECH_URGENCY. Add AI history results for researched, blocked, unaffordable, and duplicate requests.

Verification: headless match where the AI researches a valid technology and does not repeatedly request a blocked branch.

8

Advanced branches

Add mutually exclusive doctrines, target-specific counters, unlocks, temporary effects, map interaction, and optional building-owned research queues one at a time.

Verification: each new effect gets a focused test and a balance scenario before it enters the default data set.

14. Balance And Readability Rules

Every bonus needs a victim

If a technology improves attack, ask what it gives up: resources, armor, speed, time, another branch, or effectiveness against another target.

Do not make categories overlap too much

A heavy melee infantry unit could receive melee, heavy, and infantry bonuses. Limit stacking or make the technologies compete for the same branch.

Counter-tech should be readable

“+15% against cavalry” is interesting only if the player can identify cavalry, understand the effect, and react before spending resources.

Research time is a strategic cost

While researching, the player may not be producing another technology. This opportunity cost is often healthier than very large resource costs.

Do not heal for free by changing max HP

If a technology raises maximum HP, decide whether current HP is unchanged, proportionally changed, or capped. The safest default is unchanged current HP.

Effects must be inspectable

Players should be able to answer why a unit has its current attack, armor, speed, and cost. Hidden stacks make balance bugs feel random.

Suggested initial numbers

Broad category bonus5-10%Broad effects reach many units and should be modest.
Target-specific counter10-20%Strong only in the right matchup; make the target clear.
Trade-off doctrine8-15% positive, 4-10% negativePositive and negative values should be comparable.

15. Recommended First Vertical Slice

Build this first: one Blacksmith technology, one player queue, one effect, one prerequisite, one save table, and one UI card. 
Technology: Tempered Blades
Prerequisite: player owns a ready Blacksmith
Cost: 100 wood + 75 gold
Research time: 180 fixed ticks
Effect: own units with typeMelee deal +10% attack
Scope: existing and newly created units
Exclusive: no
AI: selected when melee army ratio and TECH_URGENCY are high
  1. Research it in the player queue.
  2. Complete it through a deferred command.
  3. Store completion in Player.
  4. Apply the effect in Unit::getAttackVal().
  5. Display the exact source filter in the UI.
  6. Save and load completion state.
  7. Test it against a non-melee unit and against a melee unit.

Once this vertical slice works, add a second technology with a target filter, such as “ranged units deal +15% against cavalry.” That proves the architecture can express both broad specialization and matchup-specific counterplay before adding more complex doctrines.
