1. Short Version

Recommendation: keep data.db for globally shared units, buildings, resources, and base levels. Put map-owned age definitions and reusable conditions in maps.db. Save only the selected map and live world-age progress.

Do not merge data.db and maps.db solely because age rules become mission-specific. The files have useful, separate responsibilities: the former is the shared gameplay catalogue; the latter is map and mission configuration.

If one physical map always has exactly one game mode, map-owned age data is enough. If several maps should share the same progression, use an age profile. If one terrain map can host several scenarios with different progression, add a mission that selects both a map and an age profile.

STATIC

Content definition

Ages, logical stages, reusable conditions, and map age order define the rules of a mission map.

RUNTIME

Save continuation

Current age and reached-age history describe one in-progress match.

2. Current System

The implementation loads map-owned world-age content from Data/map/maps.db. Each map selects an ordered list of candidate age IDs. A candidate has a logical stage and one or more reusable conditions; explicit age_transition rows select the direct candidates for the current branch, while map-list order resolves ties.

data.db stores shared level gates as age_stage. Saves persist the selected map in config.map, then restore current age and reached-age history against that map's catalog.

Current static content

data.db
  unit_level(..., age_stage)
  building_level(..., age_stage)

maps.db
  map(id, xmlName, name, age_ids)
  age(id, stage, name)
  condition(id, metric, target)
  age_condition(age_id, condition_id)

 saves/<name>.db
  config(map, ...)
  world_age(current_age, age_started_tick, history)
Current behavior: WorldAgeController records the selected age route and exposes its logical stage. A level requiring stage 2 is available after any candidate age at stage 2 is reached.

3. Static Content And Save State

Static definitions answer what the match can do. Save state answers what this specific match has already done. They must remain separate. This keeps balance edits centralized, avoids embedding a copy of the age catalog in every save, and preserves one validation path for all maps using the catalog.

The save references content that already exists in the installed map database. It stores only enough state to continue the same route deterministically.

4. Storage Options

The active map-owned catalog is the current implementation. The alternatives below are retained as future design options only; they are not tables present in the checked-in databases.

4.1 Option A: One Global Graph In data.db

Schema shape

data.db
  world_age_node(id, name)
  world_age_transition(
      id, from_node, to_node,
      metric, target
  )

Legacy proposal; this is not the active implementation.

Use when

Every map would deliberately use the same graph, the same conditions, the same node IDs, and the same level-unlock meaning.

It cannot represent a short tutorial with three ages and a standard map with a branching seven-node graph without special-case code.

4.2 Option B: Graph Directly Owned By Each Map

Schema shape

maps.db
  map(id, xml_name, name)
  map_age_node(map_id, id, name)
  map_age_transition(
      map_id, id, from_node, to_node,
      metric, target
  )

Each map can have any graph shape.

Use when

One terrain map permanently represents one mission and no two maps need to share the same progression definition.

Two maps with the same age rules duplicate all profile rows. Map ownership also becomes misleading if one terrain map later gains a tutorial and a skirmish mode.

4.3 Option C: Reusable Age Profiles In maps.db

Schema shape

maps.db
  map(..., age_profile_id)
  age_profile(id, name, ...)
  age_node(profile_id, id, name)
  age_transition(profile_id, id, ...)

Maps select reusable, validated progression content.

Use when

Maps can differ in ages, while several maps may still share a standard, tutorial, or long-match progression profile.

This adds one concept and one foreign key, but avoids duplicated graphs. This is the recommended default.

4.4 Option D: Separate Missions Select Map And Profile

Schema shape

maps.db
  map(id, xml_name, name)
  mission(id, map_id, age_profile_id, name)
  age_profile(...)
  age_node(...)
  age_transition(...)

One terrain map can host several scenarios.

Use when

A terrain map may support a tutorial, a normal skirmish, a survival scenario, or campaign missions with different progression.

New-game UI, save configuration, and loading must select and persist mission_id, not just map_id.

4.5 Rejected: Copying The Graph Into Every Save

Do not use saves as the normal owner of node and transition definitions. It duplicates static data, makes balancing edits invisible to existing saves, permits malformed copies of a graph, and makes one profile difficult to validate and reuse. A save should refer to an installed profile and preserve only runtime continuation state.

5. Comparison

OptionBest fitStrengthsCosts and limits
A. Global data.db graphOne universal progression for all maps.Smallest implementation; one global set of level gate IDs.No mission-specific graph shape, targets, or timing without changing global content. This is a rejected legacy option; the active implementation is map-owned.
B. Map-owned graphMap always equals mission.Easy selection through the already saved map ID; each map can have independent nodes and transitions.Duplicate profiles across maps; terrain cannot be reused cleanly for different scenarios.
C. Reusable profileDifferent maps and reusable progression types.No graph duplication; profile-specific timing and gates; content authors can reuse standard profiles.Requires profile loading, selection, and validation. Map-to-profile assignment must remain stable for saves.
D. Mission selects map and profileMultiple gameplay modes on one terrain map.Most expressive ownership; map art and scenario rules remain independent; profiles are reusable.More UI and save/load work; every new game needs an explicit mission selection.

The profile option separates terrain selection from progression reuse. The mission option additionally separates a scenario from its terrain.

6. Recommended Profile Schema

Use this model when a selected map normally determines the progression profile, but profiles should be reusable. The following is a proposed schema for maps.db, not a description of current tables.

-- Existing map row gains one profile selector.
map (
    id PRIMARY KEY,
    xml_name NOT NULL,
    name NOT NULL,
    age_profile_id NOT NULL
)

age_profile (
    id PRIMARY KEY,
    name NOT NULL,
    hold_ticks INT NOT NULL,
    timeout_ticks INT NOT NULL
)

age_node (
    profile_id INT NOT NULL,
    id INT NOT NULL,
    name TEXT NOT NULL,
    PRIMARY KEY (profile_id, id),
    FOREIGN KEY (profile_id) REFERENCES age_profile(id)
)

age_transition (
    profile_id INT NOT NULL,
    id INT NOT NULL,
    from_node INT NOT NULL,
    to_node INT NOT NULL,
    metric INT NOT NULL,
    target REAL NOT NULL,
    PRIMARY KEY (profile_id, id),
    FOREIGN KEY (profile_id) REFERENCES age_profile(id)
)

The composite keys mean node ID 3 is unique only within one profile. This is valid because the active profile identifies the graph in which a node or transition is resolved. Keep IDs stable within a released profile whenever existing saves must remain loadable.

Validation remains required: SQLite foreign keys alone do not prove that a transition's from_node and to_node belong to its profile_id. Runtime validation must reject missing endpoints, self-edges, invalid metrics, non-positive targets, unreachable nodes, and cycles.

A profile may contain a different number of nodes, branch points, convergence points, conditions, and timing policy than any other profile.

7. Mission Schema

Use an explicit mission when the terrain choice and the progression choice must vary independently. For example, the same terrain may be used by a short onboarding mission, a normal skirmish, and an extended campaign scenario.

map (
    id PRIMARY KEY,
    xml_name NOT NULL,
    name NOT NULL
)

mission (
    id PRIMARY KEY,
    map_id INT NOT NULL,
    age_profile_id INT NOT NULL,
    name NOT NULL,
    description TEXT NOT NULL,
    scenario_kind INT NOT NULL,
    FOREIGN KEY (map_id) REFERENCES map(id),
    FOREIGN KEY (age_profile_id) REFERENCES age_profile(id)
)

age_profile (...)
age_node (...)
age_transition (...)

With this model the save should identify mission_id. The mission resolves the terrain map and age profile. Saving only map_id would be ambiguous because one map can now select multiple profiles.

A different mission can reference the same terrain map and select another profile without duplicating the terrain or pretending that one map has only one scenario.

8. Future Mission Content

Future design only: missions, scenarios, objectives, victory, and failure rules are not implemented by the current game. This section identifies the appropriate ownership boundary without committing the runtime to a complete objective system yet.

A mission is the natural static owner for scenario-specific content. It already identifies the terrain map and age profile, so it should also define the information that distinguishes a tutorial, skirmish, survival scenario, campaign level, or challenge on that terrain.

ContentRecommended ownerWhy
Mission name, description, briefing, scenario kindmission in maps.db.Static authoring content selected before a match starts.
Terrain, terrain XML, resolution, terrain-specific placementsmap in maps.db.Reusable physical world data; several missions may share it.
Age graph, timing, and profile-specific unlock gatesage_profile and child tables in maps.db.Reusable progression rules; they need not be tied to one terrain or objective set.
Starting players, teams, nations, resources, and scripted starting entitiesMission-owned scenario tables in maps.db.These are scenario setup rules, not universal unit or building definitions.
Objective definitions and success/failure conditionsMission-owned objective tables in maps.db.They describe what the mission asks the player to do, independent of current progress.
Current objective completion, counters, timers, and triggered script stateSave runtime tables, only when a mission can be saved mid-progress.These values change during a specific match and must survive save/load.

8.1 Minimal Future Schema Direction

Keep the initial schema descriptive and specific. Do not create a generic scripting language or an unbounded key/value table before objective types are known. A future vertical slice can begin with a small, explicitly supported set of objective kinds.

-- Static content in maps.db. Proposed; not implemented.
mission (
    id PRIMARY KEY,
    map_id INT NOT NULL,
    age_profile_id INT NOT NULL,
    name TEXT NOT NULL,
    description TEXT NOT NULL,
    scenario_kind INT NOT NULL
)

mission_player (
    mission_id INT NOT NULL,
    slot INT NOT NULL,
    team INT NOT NULL,
    nation_id INT NOT NULL,
    controller_kind INT NOT NULL,
    starting_food INT NOT NULL,
    starting_wood INT NOT NULL,
    starting_stone INT NOT NULL,
    starting_gold INT NOT NULL,
    PRIMARY KEY (mission_id, slot)
)

mission_objective (
    mission_id INT NOT NULL,
    id INT NOT NULL,
    objective_kind INT NOT NULL,
    subject_kind INT NOT NULL,
    subject_id INT NOT NULL,
    target_value INT NOT NULL,
    target_player_slot INT NOT NULL,
    order_idx INT NOT NULL,
    is_required INT NOT NULL,
    title TEXT NOT NULL,
    description TEXT NOT NULL,
    PRIMARY KEY (mission_id, id)
)

Possible first objective kinds are deliberately narrow: reach an age node, own a unit or building count, accumulate a resource, survive for a tick duration, or eliminate a target player. The subject_kind and subject_id pair identifies what is measured: an age node, database unit/building/resource, or player slot. target_value is the required amount, duration, or boolean threshold. This remains a finite enum-based contract, not an unbounded key/value scripting format.

Mission-owned starting entities should reference globally defined unit and building IDs in data.db; the mission decides which entities are present, while data.db still defines their base properties. Initial placement may later be stored as a mission spawn table or authored through an existing scene/map format, but the mission should remain the logical owner of the rule.

8.2 Runtime State For Future Objectives

Many basic objectives can be recalculated from authoritative game state after loading. Persist objective runtime state only when it cannot be derived, such as a timer already spent, a one-time trigger that fired, a sequential objective stage, or a counter that records historical events.

-- Save data only when objective continuation needs it. Proposed; not implemented.
mission_state (
    mission_id INT PRIMARY KEY,
    outcome INT NOT NULL,
    active_objective_id INT NOT NULL
)

mission_objective_state (
    mission_id INT NOT NULL,
    objective_id INT NOT NULL,
    state INT NOT NULL,
    progress INT NOT NULL,
    started_tick INT NOT NULL,
    completed_tick INT NOT NULL,
    PRIMARY KEY (mission_id, objective_id)
)

Static mission tables define the scenario. Save tables contain only the changing state that is required to resume that scenario.

9. Conditions And Timing

The active model uses map-owned age candidates. Each age joins one or more reusable conditions, and all joined conditions must be true on the same simulation tick.

RequirementSimplest representationWhen to add more structure
Worker or army average thresholdcondition.metric plus target.Reuse one condition row whenever the threshold is shared.
Several conditions must all be trueSeveral age_condition rows for one age.All joined rows are evaluated in the same tick.
Alternative candidates at one stageSeveral age IDs with the same age.stage.Map age_ids order resolves same-tick ties.
 
condition(id, metric, target)
age_condition(age_id, condition_id)

Conditions are shared static rows. The join is deliberately separate so the same worker or army threshold can be attached to several age candidates.

10. Level Gates

The existing fields unit_level.age_stage and building_level.age_stage are shared logical stage gates in data.db. They remain independent of which map age candidate wins within a stage.

When profiles differ, choose one of two valid contracts. Do not accidentally mix them.

Shared logical stages

Keep level gates meaningful by stage. Candidate age IDs may differ by map, while stage 1, stage 2, and stage 3 keep the same progression meaning.

The shared age_stage columns remain in data.db.

Profiles have less freedom because their IDs and milestone meanings are partly global.

Profile-specific gates

Let every profile define IDs independently. Resolve unit and building availability through the selected profile's gate rows.

age_level_gate (
    profile_id INT NOT NULL,
    entity_kind INT NOT NULL,
    level_id INT NOT NULL,
    required_node_id INT NOT NULL,
    PRIMARY KEY (
        profile_id, entity_kind, level_id
    )
)

Maximum mission flexibility.

Availability lookup, data loading, and validation become profile-aware.

Node IDs are identifiers, not age numbers. A gate requiring node 3 asks whether the exact node with ID 3 was reached on the selected route. It does not mean “the third age.” A graph may branch, converge, skip an ID, or have more/fewer nodes than another profile.

The graph route matters. An exact convergence node can unlock shared content after more than one branch without treating node ID as an ordinal age position.

11. Save Contract

A save must identify enough static content to reconstruct the same graph, then retain only the mutable state needed to continue it. Which identity it stores depends on the selected option.

Content ownerStatic identity persisted by saveWorld-age continuation persisted by save
Map-owned agesconfig.map.Current age, age start tick, and reached-age history.
 
Map-selected profile save shape

config
  map = 1

  world_age
  current_age = 3
  age_started_tick = 1820
  history = '0,1,3'
Compatibility rule: age IDs are saved references. Keep them stable within the selected map catalog. If a release changes or removes them, make an explicit choice to migrate affected saves, keep the old catalog available, or reject old saves with a clear incompatibility error.

Saving age_profile_id as an additional diagnostic field is optional for map-selected profiles because the map already determines it. It can still improve error messages if map content changed since the save was made. It is mandatory in spirit, though not necessarily as a separate column, that loading verifies the route against the graph selected by the saved map or mission.

12. Migration And Implementation

The active design is a map-owned catalog, not a global graph. Load and validate ages, reusable conditions, map order, and stage gates before constructing the controller. Preserve deterministic average-metric evaluation, candidate order, history, and route restoration.

1

Keep the owner

The active implementation keeps the age catalog in maps.db, with each map selecting ordered candidate IDs through map.age_ids.

2

Maintain static map content

Create age, condition, and age-condition rows in maps.db. Keep age IDs stable and place candidate IDs in each map's ordered age_ids list.

3

Validate catalogs

DatabaseCache loads reusable conditions and age joins. It validates age references, condition metrics and targets, ordered stage progression, and level-stage bounds.

4

Select at simulation creation

LevelBuilder resolves the selected map before Simulation is created. WorldAgeController receives that map's catalog and ordered age list.

5

Resolve level availability

Unit and building levels use shared age_stage gates. A level is available when the selected age reaches at least its required logical stage.

6

Protect save loading

Load the map first, then restore world_age and validate its current ID and history against that map. Add an explicit migration or incompatibility error if age IDs change.

Focused Verification

  • Load a short linear profile, a branching profile, and a terminal single-node profile.
  • Verify all configured players contribute to transition averages under the current implementation.
  • Save and load while the current age timeout is in progress.
  • Save and load after each candidate age route reaches a later stage.
  • Reject a save whose current age or history route does not belong to its selected map catalog.
  • Verify shared logical level gates after both candidate ages in a stage.
